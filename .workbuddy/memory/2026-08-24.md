## Redis/worker 未启动导致 DM pipeline 卡死排查与恢复

**症状**：剧本解析在切分为 N 个分片后停止，job 卡在 `extracting` 状态。

**根因**：`.env.local` 设置 `CELERY_EAGER=false`（走真实异步链路），但本机未启动 Redis 和 Celery worker。`prepare_document` 通过 `dispatch_pipeline` → `apply_async` 把 chord 任务派发到 Redis broker，但无 worker 消费，pipeline 停在分片阶段。

**影响范围**：2 个 job 卡死：
- `1a118be8` 猫岛谋杀循环：卡在 extracting（0/5 shards）
- `1c326ff9` 木夕僧之兮：卡在 embedding（9/33 chunks）

**修复步骤**：
1. 启动 Redis：`Start-Process "C:\Program Files\Redis\redis-server.exe" -ArgumentList "--port","6379"`
2. 启动 Celery worker：`.venv/Scripts/python.exe run_worker.py`（threads 池，concurrency=6）
3. 标记旧 job 为 cancelled，创建新 job 并调用 `dispatch_pipeline(force=True)` 重新派发
4. 确认 pipeline 推进：猫岛 → generating_qa（128 块），木夕 → embedding（6/33 块）

**教训**：本地开发需确保 Redis + worker 在后端启动前/同时运行。`.env.local` 的 `CELERY_EAGER=false` 要求 Redis 可达。

## qa-titles 接口加 Redis 缓存

**需求**：剧本详情的 `/qa-titles` 接口（`GET /scripts/{id_or_code}/dm-guide/qa-titles` 与 `GET /dm-guide/qa-titles`）加 Redis 缓存。

**实现**（70 测试全过）：
1. `redis_cache.py` 新增**域级（scope）版本号**：`get_scope_version(scope)`（异步读）+ `bump_scope_version_sync(scope)`（同步 INCR，给 Celery worker 用，独立同步客户端 + 30s 失败冷却）。与全局 `bump_version` 分离，QA 缓存失效不牵连剧本列表缓存。
2. `dm_store.py` 定义 `QA_TITLES_CACHE_SCOPE = "dm-qa-titles"` 与 `qa_titles_cache_scope(code)`，API 侧与 worker 侧共用同一口径。
3. `dm_service.qa_title_chain` cache-aside：key=`jbs:cache:dm-qa-titles:{code}:{scope_version}`，TTL=`DM_QA_CACHE_TTL`（默认 600s）。缓存整棵 QATitleChain，但 `script_title` 随调用方而定不进缓存，命中后覆写。
4. `dm_ingest.py` 三个失效点（`_invalidate_qa_titles_cache`）：finalize 收尾后、force 重跑 purge 后、幂等 skip 下线旧版本后。失效失败静默靠 TTL 兜底。

**要点**：scope 版本号天然规避「查询中途 bump 导致回填旧数据」的竞态——旧版本 key 永远不会被读到，TTL 到期自然淘汰。
