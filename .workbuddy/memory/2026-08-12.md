## 剧本重传去重修复（杜绝假续集编码 shan-mu-gui-2）
- 现象：同一本《山母鬼》上传两遍，第二遍生成 `shan-mu-gui-2`。根因不是续集逻辑，而是 `slugify`+`_generate_code` 的防重名自增序号；更深根是 `find_existing(title)` 只做标题精确匹配，两次上传标题略有差异（文件名/副本/扩展名）就没去重，走了新建分支。
- `_generate_code` 的 `-N` 后缀语义 = 防重名自增，不等于「第 N 部」；且 `shan-mu-gui-2` 会与真续集《山母鬼2》的 slugify 结果撞车，无法区分。
- 修复：在 `repository.py` 新增 `normalize_title_key`（去扩展名/首尾空白/系统复制噪音「副本」「（1）」，保留用户有意序号「山母鬼2」「山母鬼 第二部」）；`find_existing` 用归一化钥匙同时匹配 `title` 与 `aliases`；创建/合并时把归一化钥匙写入 `aliases`，使重传稳定合并回原行。
- 新增 `tests/test_title_dedup.py` 锁住行为（沙箱 venv 缺 httpx 跑不了，需在已装依赖环境运行）。
- 待办：用户库里已有的 `shan-mu-gui-2` 假重复行建议软删清理；真续集仍按「不同标题→不同 slug」区分，必要时加 `series_code`/`episode`/`prequel_code` 显式关联（本期未做）。

## 剧本 code 生成：移除自动序号 2/3 后缀
- 用户要求：剧本 code 经 pinyin 库、以标题为入参生成；**不自动生成 2、3 这类序号**，**仅当标题本身含数字时** code 才带数字（数字来自标题原文，如「山母鬼3」→`shan-mu-gui-3`）。
- 改 `app/services/script_service.py` 的 `ScriptService._generate_code`：删除 `for suffix in range(2,12)` 的 `-2/-3` 自增后缀循环与最终 `-{uuid}` 兜底后缀。现在直接返回 `slugify(title)`（空标题才退化为随机短码）。
- `slugify` 原样保留标题里的数字/字母，配合本改动即满足「仅标题含数字才带数字」。DM 导入路径（`dm_ingest.py`/`dm_service.py` 直接用 `slugify`）行为一致，也不会再产生 `-2` 假续集。
- 冲突处理：重名不再偷偷加 `-2`，改由 `_create_new` 现有唯一性校验抛 `ConflictError`（「剧本编码已存在」）。真正的跨标题同音撞码属罕见情况，宁可报错也不造假续集。
- 同步更新了模块 docstring（第 2 点）与 `slugify`/`_generate_code` 的 docstring 示例。`py_compile` 通过；沙箱缺 httpx/pypinyin 跑不了整测试，需在已装依赖环境验证。

## 剧本 code 生成：去掉 code 唯一性校验（用户后续要求）
- 用户补充：「不需要校验，因为我可能需要多个文档进行向量化操作」。于是移除 `_create_new` 里的应用层 code 唯一性校验（`if get_by_code(code): raise ConflictError`），并把不再使用的 `ConflictError` 从 import 移除。
- 现在 code 由 `_generate_code` 派生后直接使用，既不自动加 -2/-3，也不再主动查重拦截。
- 注意：数据库 `sql/scripts.sql` 里 `code` 仍有唯一约束 `uq_scripts_code`（注释说它是 PostgREST upsert 的前提，且 `get_script`/`get_by_code` 靠它按 code 解析）。所以真正的同音撞码（如「测试」「册史」都→`ce-shi`）在写入时仍会被数据库唯一约束拒绝，只是不再有应用层的友好 `ConflictError`。是否需要一并 DROP 该唯一约束以支持「多文档/多剧本共用同一 pinyin code 做向量化 scope」尚未确定，已向用户确认。

## DM ask 接口 500 修复（生产环境 jbsttj-backend-production.up.railway.app）
- 现象：所有 `POST /api/v1/dm-guide/ask`（mode=hybrid/qa）都返回 500；若剧本未索引则正确返回 409，因此定位到「有 QA 命中」的分支。
- 根因：`ask()` 用 `QAHit` 组装 `AskSource` 时取了 `h.section_path / h.page_start / h.page_end`，但 `QAHit` 模型及其构造器 `_to_qa_hit` 都没声明/填充这三个字段（只有 `ChunkHit` 有）。访问不存在属性 → `AttributeError` → 全局 handler 兜底成 500。DB 的 `script_dm_qa` 实际有 `section_path/page_start/page_end` 列、`match_dm_qa` RPC 也返回了它们，只是没接进模型。
- 修复：`app/schemas/dm_guide.py` 的 `QAHit` 补 `section_path/page_start/page_end`；`app/services/dm_service.py` 的 `_to_qa_hit` 从 row 读取并填充（section_path 兼容 text[] 数组与历史逗号串）。`tests/test_dm_guide_ask_request.py` 新增回归测试 `test_qa_hit_carries_page_and_section`（6/6 通过）。
- 部署：改动在代码层，生产需重新部署（Railway 重建）后才生效。
