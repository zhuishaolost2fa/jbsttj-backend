# 2026-08-12

## 头像上传链路排错（/v1/auth/me/avatar）

连续踩了三个坑，根因都是「数据库/OSS 实际状态与代码/迁移预期不一致」：

1. **PGRST204**：`profiles.avatar_object_key` 不在 PostgREST schema cache。
   → 刷新缓存：`NOTIFY pgrst, 'reload schema';`（Supabase Dashboard → Database → API → Reload）。

2. **23502 not-null violation**：`avatar_color` 在代码里被当作「可清空(null)」使用（上传头像/编辑资料都写 null），但 `sql/profile.sql` 定义成 `integer not null`。
   → 已把 `profile.sql` 两处放宽为可空（`integer default 0 check (... between 0 and 7)`），并加了幂等 `alter column ... drop not null` 兜底。线上库需手动执行一次 `alter table public.profiles alter column avatar_color drop not null;`。

3. **头像 URL 打不开（403）**：`upload_avatar` 原先用 `oss.public_url()` 拼出裸 bucket 公网域名（如 `jbs-store.oss-cn-hangzhou.aliyuncs.com/...`），但对象默认私有 + 阿里云默认「阻止公共访问」，直接访问 403。
   → 已改为统一存储后端代理地址 `/api/v1/files/avatar/{user.id}`（files.py 的 get_avatar，服务端凭证回源、无需鉴权、不依赖 bucket 公开读）。改了 `app/api/v1/auth.py`（去掉 oss 依赖、avatar_url 取值改代理）。

## 结论/约定
- 头像回源走代理接口，不要再依赖 OSS 裸公网 URL 或 bucket 公共读（安全风险 + 默认阻止公共访问）。
- 存量老用户 avatar_url 仍是坏 OSS 链接，需重新上传一次（新代码会存正确代理 URL），或跑 SQL 改写为 `/api/v1/files/avatar/{id}`（同源前端才适用相对路径）。
- 注意：`public_url` 只拼 URL 不校验可达性；`oss_endpoint` 配了就返回非空 URL，导致代理兜底永不被触发——这是「伪配置可用」陷阱。

## 头像方案最终定案：B（对象级 public-read + OSS/CDN 直链）
用户选了方案 B（去掉后端中转，浏览器直连 OSS/CDN）。
改动：
- `oss.py` 新增 `set_object_acl(key, acl)`，内部用 `client.put_object_acl(PutObjectAclRequest(bucket,key,acl=...))`（V2 SDK 的 PutObjectRequest 同时有 `acl`/`object_acl` 两个字段语义含糊，故用独立的 put_object_acl 调用最稳）。失败时若 AccessDenied 会给出“请关闭 bucket 阻止公共访问”的明确报错。
- `file_service.simple_upload` 新增可选 `acl` 参数：上传后（含秒传复用分支）调用 `set_object_acl`；普通文件不传 → 保持私有。
- `auth.upload_avatar` 恢复 `oss` 依赖，`simple_upload(..., acl="public-read")`，`avatar_url` 改回 `oss.public_url(object_key) or 代理兜底`。

**关键前置（必须做，否则上传会直接 500）**：阿里云 OSS 控制台 → `jbs-store` 桶 → 权限管理/安全设置 → **关闭「阻止公共访问」（Block Public Access）**（账号级若强制也需关）。否则对象设 public-read 被拒。
部署后老用户需重新上传一次头像（生成正确 public-read 对象 + 直链 URL）。

## 上传新头像时清理旧 OSS 对象
用户要求重新上传头像时删除 OSS 上的旧头像文件，避免残留。
改动 `auth.upload_avatar`：
- 上传前用 `db.select_one("profiles", filters={"id": f"eq.{user.id}"})` 取旧 `avatar_object_key`；
- 上传+upsert 成功后，若 `old_object_key` 存在且 ≠ 新 `object_key`，调用 `oss.delete_object(old_object_key)`（oss.py:490 已有此方法）；
- 删除失败仅 `logger.warning`，不阻断本次头像更新（best-effort）。
注意：新 key 由 `simple_upload` 用 uuid 生成，每次上传都不同，故旧 key 始终会被清理。
