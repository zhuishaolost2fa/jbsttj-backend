## 从零搭建文件上传服务（FastAPI + 阿里云 OSS + Supabase）

在空工作区 `jbsttj-backend` 中建立完整后端服务，需求：对外暴露上传接口、底层用阿里云 OSS、
需用户鉴权、数据库用 Supabase、前端分片上传。

### 架构决策

- **分片上传采用「前端直传 + 后端签名」**：后端只签发预签名 PUT 地址、记账、合并分片，
  文件数据不流经应用服务器。同时保留一条服务端代理上传通道（`PUT /uploads/{id}/parts/{n}`）
  作为 OSS 无法直连时的降级方案。
- **OSS 是上传进度的唯一可信来源**：`complete` 前重新 `ListParts` 校验完整性，
  前端上报的 ETag 仅作交叉校验，防止漏报/篡改导致合并出损坏文件。
- **鉴权**：校验 Supabase 签发的 JWT，同时兼容传统 HS256 密钥与新版 ES256/RS256 JWKS
  （JWKS 带 TTL 缓存，遇未知 kid 主动刷新以应对密钥轮换）。另有可选的 `X-API-Key`
  + `X-User-Id` 服务间调用通道。
- **数据库**：不引入 supabase-py，直接用 httpx 异步调 PostgREST，全异步无阻塞。
  后端用 service_role key 会绕过 RLS，因此**仓储层每条查询都强制带 user_id 过滤**；
  schema.sql 中另配 RLS 策略供前端直连时兜底。
- **秒传**：客户端算内容指纹（头/中/尾各 2MB + 体积 + 文件名的 SHA-256），命中则复用同一
  OSS 对象。因此 `files.object_key` 刻意不加唯一约束，删除时按引用计数决定是否物理删除。

### 两个关键坑（已在代码与 README 中固化）

1. **预签名 URL 的 Content-Type 必须两端一致**：分片 PUT 统一用
   `application/octet-stream`（常量 `PART_CONTENT_TYPE`），否则 OSS 返回
   `SignatureDoesNotMatch`。最终对象的真实 MIME 在 `InitiateMultipartUpload` 时确定。
2. **Bucket CORS 必须把 ETag 放进 expose-headers**，否则前端 JS 读不到分片 ETag。
   已写成 `scripts/setup_oss.py` 一键配置（同时配 7 天清理未合并分片的生命周期规则）。

此外：服务端调 OSS 走内网 endpoint，签名给浏览器用公网/CDN endpoint，故 `OSSService`
内维护两个 Bucket 实例。

### 目录约定

### 环境注意事项（Windows 沙箱）

`[safe-delete][SAFE_DELETE_FAIL_CLOSED] windows-sandbox-recycle-bin-unavailable` 而失败。

### 迁移 OSS 层到 V2 SDK（alibabacloud_oss_v2）

用户贴的阿里云代码用的是新版 V2 SDK，故把 `app/services/oss.py` 从旧版 `oss2` 整体迁到
`alibabacloud_oss_v2`（已由用户确认"迁移服务到 V2"）。

- **关键 API 事实（已用内省 + 本地无网预签名验证）**：
  - V2 公开 API 是**同步阻塞**，**没有 AsyncClient**（只有内部 `AsyncHttpClient`）。故保留
    `run_in_threadpool` 包裹，事件循环不被阻塞，行为与 oss2 时一致。
  - 凭证：`oss.credentials.StaticCredentialsProvider(access_key_id, access_key_secret)`。
  - 配置：`oss.config.load_default()` 后设 `region / endpoint / credentials_provider /
    signature_version('v1'|'v2'|'v4') / use_cname / connect_timeout`。默认即 V4 签名
    （URL 出现 `OSS4-HMAC-SHA256`）。
  - 分片：`InitiateMultipartUploadRequest(bucket,key,content_type,metadata)` → `.upload_id`；
    `UploadPartRequest(bucket,key,upload_id,part_number,body)` → `.etag`；
    `ListPartsRequest(...,part_number_marker,max_parts)` → `.parts(Part: part_number/etag/size)
    / .is_truncated / .next_part_number_marker`；`CompleteMultipartUploadRequest(bucket,key,
    upload_id, complete_multipart_upload=CompleteMultipartUpload(parts=[UploadPart(pn,etag)]))`
    → `.etag`；`AbortMultipartUploadRequest(bucket,key,upload_id)`。
  - 预签名：`client.presign(UploadPartRequest(...), expires=timedelta(seconds=N)).url`。
    **分片预签名 URL 自动含 `partNumber` 与 `uploadId` 查询参数**，`signed_headers` 为空
    → Content-Type 不参与签名，前端带 `application/octet-stream` 不会 SignatureDoesNotMatch
    （旧 oss2 的"两端 Content-Type 必须一致"坑在 V2 下天然不存在）。
  - 下载预签名用 `GetObjectRequest(bucket,key, response_content_disposition=...)`（**专用字段**，
    不是 `params` 字典！传 params 会被忽略）。
  - **没有 object_exists**：用 `head_object` + 捕获 `ServiceError(ec=='NoSuchKey')` 判不存在。
  - 异常：`oss.exceptions.ServiceError`，OSS 错误码在 `exc.ec`（也兼容 `exc.code`）；
    `NoSuchKey/NoSuchUpload/NoSuchObject` → 映射 NotFoundError。
- **Windows 沙箱 pip 新坑**：装 `alibabacloud_oss_v2` 时因 `crcmod-plus` 要替换旧 `crcmod`
  （同名命名空间），pip 卸载旧 `crcmod` 触发 `safe-delete ... windows-sandbox-recycle-bin-unavailable`
  而失败。**解决**：先手动 `shutil.rmtree('.venv/Lib/site-packages/crcmod')` 及其 dist-info，
  再 `pip install --no-cache-dir --no-compile alibabacloud_oss_v2`（已成功装 1.3.2）。
- 已验证：oss.py 编译通过、app.main 可导入、smoke_test 27/27 仍过、V2 预签名 URL 形态正确
