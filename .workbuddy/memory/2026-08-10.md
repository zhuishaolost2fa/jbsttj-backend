## 排查「卡在 extracting」的真实根因（script-4b3ab598 / 王不见王）
- 用户纠正：Railway 上 `CELERY_EAGER=false`（之前误判本地 .env 的 true）。Railway 用 supervisord 拉起 web + 4 个 worker（dm.extract/chunk/qa/embed），broker 走 Railway Redis `${REDIS_URL}/0`。
- 直接用 Supabase REST（service_role）读 `script_dm_jobs`：该 job `status=extracting, processed_pages=0, finished_shards=0, retry_count=0, updated_at` 冻结 ~35 分钟；同表 20 页小 PDF 是 `completed`（证明 worker/broker/Supabase 整体通）。
- **元凶：`scripts.extra.dmGuide.fileSize=281MB / 369 页 ≈ 每页 730KB → 这是图片/扫描件 PDF，没有文字层**。于是 `extract_shard` 对几乎每页走阿里云 OCR 兜底（`ocr.py` read_timeout=60s，顺序执行），而进度只在整片（30 页）抽完才 `bump_job` 一次 → processed_pages 长时间停在 0，看似冻结。另有 Railway 免费档 512MB 内存跑 268MB 图片 PDF 的 OOM 死循环风险。
- 排除项：非 eager、非 broker 没配（prepare_document 已成功写入 extracting）、非 worker 启动即挂、非 OCR 永久挂（有 60s 超时且异常被吞）。
- 诊断方法：Railway 日志搜 `分片 0 OCR 兜底识别了 N 页` / `分片 0 提取完成` 判断是否慢跑；搜 `MemoryError`/`SIGKILL` 判断是否 OOM。
- 修复方向：上传前用 OCRmyPDF 转成带文字层 PDF（治本）；调低 `ocr_dpi`、升级 Railway 内存、调小 `DM_EXTRACT_PAGES_PER_SHARD`；代码上把 extract_shard 进度改为按页上报，避免大 PDF 假卡死。
- **用户贴出 Railway 日志确认根因**：`ForkPoolWorker-34 ... signal 9 (SIGKILL)` + `WorkerLostError` → 是**内核 OOM Killer 杀掉 extract worker**（不是慢）。`OCR 第 301 页失败，跳过：Connection aborted. TimeoutError('The write operation timed out')` 是内存压垮后的下游写超时症状。机制：worker 跑 268MB 扫描件逐页 OCR → 内存涨 → SIGKILL → 任务 late-ack 重回队列 → 新子进程再跑 → 再 OOM → 无限死亡循环，所以 processed_pages 永远 0、停在 extracting。OCR 能到 301 页也证明是扫描件。
- **已做的代码/配置修复**：(1) `app/services/ocr.py` 的 Aliyun OCR client 补 `config.write_timeout=60000`（之前只有 read/connect timeout，对应日志里的 write timeout 报错）；(2) `supervisord.conf` 的 `worker_extract` 加 `--max-memory-per-child=300` 安全闸，避免内核 OOM 把整个容器（web+4 worker）带走，改为 Celery 优雅回收单子进程。
- **待用户执行的治本动作**：Railway 上设 `OCR_DPI=96`（或 72）、`DM_EXTRACT_PAGES_PER_SHARD=10` 缩小单任务内存；升级 Railway 内存档或把 `worker_extract` 拆成独立服务独享内存；上传前用 OCRmyPDF 给扫描件加文字层（最优，彻底免逐页 OCR）。

## 支持 Word(.docx) 手册，彻底免 OCR（用户诉求）
- 用户要求支持 Word 格式，从源头避开扫描件 OCR 的 OOM 问题。已实现并离线验证通过。
- 核心设计：新增 `app/services/doc_extract.py`，用 python-docx 解析 .docx，产出与 `pdf_extract` **同构的 `TextBlock`/`ShardResult`**（标题层级用 Word 样式名 Heading N/Title 映射，比 PDF 字号猜测更准；`font_size=0` 让 `calibrate_headings` 自动跳过重校准；表格行并成 `table` 块；无真页码 → 打「伪页码」每 `dm_docx_blocks_per_page`(默认40)个单元算一页，保证跨片续接 `head.page-tail.page<=1` 仍成立）。下游 `merge_shards/strip_noise/build_section_paths/chunk_blocks` **零改动复用**。
- 改动点：(1) `config.py` 新增 `dm_extract_blocks_per_shard=400`（docx 分片单位）、`dm_docx_blocks_per_page=40`；(2) `requirements.txt` 加 `python-docx>=1.1.0`；(3) `dm_service._resolve_ref` 放开 `.pdf`/`.docx`、明确拒绝旧版 `.doc`；(4) `dm_ingest.py`：`ensure_local_pdf`→`ensure_local_file`（缓存按扩展名）、`prepare_document` 按扩展名规划分片（PDF 按页 / DOCX 按文本单元）、`extract_shard` 任务改 `unit_start/unit_end/doc_format`，DOCX 分支不做 OCR，PDF 分支 OCR 兜底保持不变；(5) 上传侧 `allowed_extensions` 为空、`.docx` 不在黑名单，天然放行。
- 离线验证：构造含 Title/Heading1/Heading2/正文/表格的样例 .docx，跑通 `doc_extract→merge_shards→strip_noise→calibrate_headings→build_section_paths→chunk_blocks`，标题层级与表格内容均正确保留，断言通过；全部改动文件 `py_compile` 通过。
- 注意：DOCX 文档 `total_pages` 存的是「伪页码总数」（单元数/40 向上取整），前端「页数」对 Word 实际表示文本单元规模；检索结果出处 `page_start/page_end` 为伪页码，语义上等于段落定位，可接受的展示近似。

## 修复 `extract_shard` 的 UnboundLocalError('get_settings')（docx 解析报错）
- 现象：解析 .docx 剧本时报 `UnboundLocalError: cannot access local variable 'get_settings' where it is not associated with a value`，Celery chord 直接挂掉。
- 根因：Python 编译期按整函数体判定作用域。`extract_shard` 内 OCR 兜底分支有一行 `from app.core.config import get_settings`（第419行），import 即赋值，使 `get_settings` 被当成函数局部变量贯穿整个函数；而 docx 分支在 `blocks_per_page=get_settings().dm_docx_blocks_per_page`（第398行）处先于 OCR 分支使用它，此时局部尚未赋值 → 抛错。PDF 不会走第398行故不受影响（解释了为何只有 Word 文件报错）。
- 修复：`app/tasks/dm_ingest.py` 删除 OCR 分支里多余的局部 `from app.core.config import get_settings`（模块顶层第56行已导入全局）。OCR 的 `from app.services.ocr import ...` 懒加载保留。改完 `py_compile` 通过。
- 经验：函数内若已存在同名模块级导入，切勿再在局部 `import` 同名符号重新赋值，否则会把全局名遮蔽成本地未绑定变量，且只在特定代码路径（如 docx 早于 import 使用）才触发，极难复现。
- 验证：(1) 字节码层面断言 `get_settings` 在 `extract_shard` 中解析为 GLOBAL（co_names）而非 LOCAL（co_varnames）；(2) 本地 venv 装了 python-docx（之前只装过 PDF 侧依赖），用样例 docx 端到端直调 `extract_shard.run(doc_format='docx')`，成功返回 6 个块（标题/标题层级/正文/表格行合并均正确）。

## 顺带修复：docx 不应走按页 OCR 兜底
- 端到端测试暴露第二个 bug：`extract_shard` 底部共享的 OCR 兜底对 docx 也生效。docx 的 `page_start/page_end` 是**文本单元序号**（如 1–400/片），而块的 `.page` 是**伪页码**（每 40 单元一页，如 1–10），于是 `need_ocr` 算出几百个幻影「页」，每片空跑几百次 `render_page_png`（对 .docx 全部报 "page not in document"，日志爆炸）。
- 修复：`need_ocr` 计算加 `doc_format == "docx"` 时直接置空，只有 PDF 才按页查缺补 OCR。复跑端到端测试：docx 路径零 OCR 调用，干净通过；PDF 分支逻辑未变。`py_compile` 通过。
