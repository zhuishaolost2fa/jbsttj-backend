  渠道取值/模板/超时在 `_validate` 里校验（**凭证缺失不报致命错**，只降级）。

  在**真正新建**后 `asyncio.create_task` 投递通知；走 service 层而非 BackgroundTasks，
  这样 HTTP 和内部调用行为一致。
- 触发时机：新建 ✅ / 重复幂等 ❌ / 复活（cancelled→pending）由 `NOTIFY_ON_REVIVE` 控制默认关 /
  409 已解析 ❌。通知正文含「累计 N 人求过」（`_pending_count` 查 `leaderboard_rows`）。

## 方案：微信小程序端微信登录（未落地，仅出方案）

需求：小程序端实现微信一键登录，前后端改造方案。

### 核心结论
难点不是调微信接口，而是「微信用户怎么变成现有 Supabase 用户」—— 所有业务
都以 `CurrentUser.id`（Supabase JWT 的 sub = auth.users 的 uuid）为准。

选定方案：**`user_identities` 映射表 + GoTrue 托管账号 + password grant 换真 token**。
- 首次登录：code2session → openid → admin 建占位邮箱账号（`email_confirm=True`，
  密码 = `HMAC(WECHAT_LINK_SECRET, openid)` 派生的确定性密码）→ password grant。
- 再次登录：命中映射表 → 直接 password grant（2 次外部 HTTP，无额外开销）。
- 返回 `TokenResponse` 与 `/auth/login` **完全同构** → 前端 `tokenManager.setSession()`
  照旧，`/auth/refresh`、401 拦截、退出登录全不用动，业务代码零改动。
- 被否的备选：A 自签 JWT（要自己实现 refresh，ES256 项目签不了）；
  C Supabase 原生第三方登录（不原生支持微信，需自建 OAuth IdP）。

### 关键坑（记下来）
- 占位邮箱用 `sha256(openid)[:20]` 而非 openid 原值，否则 openid 会经 `/auth/me` 泄露。
- GoTrue admin 建号必须 `email_confirm=True`，否则占位邮箱永远收不到验证邮件、
  password grant 被拒。
- 微信 `access_token` 是全局的，重复获取会让旧 token 5 分钟内失效 → 多 worker
  互相踢。必须用 `stable_token` 接口。
- `code` 一次性、5 分钟有效，前端不能拿旧 code 重试整个登录流程。
- profiles 加 `provider` 列：微信用户没有真邮箱，前端据此隐藏改密码/改邮箱入口，
  否则会把 `wx_xxx@wechat.local` 占位邮箱糊到用户脸上。

### 产出
- `docs/wechat-miniapp-login.md`：完整方案（含后端 5 个文件 + 前端 4 个文件的完整代码）
- `sql/wechat_auth.sql`：`user_identities` 表 + profiles.provider 列（幂等）

### 阻塞项（用户必须先解决）
1. `SUPABASE_ANON_KEY` 仍是无效占位符 → password grant 需要 apikey。
   要么换真 key，要么把 `SupabaseAuth._headers()` 改用 service_role key 当 apikey。
   —— 见下方落地记录：**已确认是真 key，此项不再阻塞**。
2. `project.config.json` 的 appid 是 `touristappid`，必须换真实 AppID。
3. request 合法域名需配后端域名（https + 443，不支持 IP/自定义端口）。
4. 「获取手机号」需企业主体 + 认证 + 付费，个人号跳过。

## 落地：微信登录后端代码（不做手机号绑定）

用户拍板：不做手机号绑定，直接落后端代码。

### 实测确认（推翻旧记录）
`.env` 的 `SUPABASE_ANON_KEY` **是真实 anon JWT**（payload `role: anon`），
不是占位符 —— 记忆里那条「无效占位符导致 401」已过期。但顺手把
`SupabaseAuth._headers()` 的 apikey 改成 `anon or service_role` 回落
（GoTrue 两者都接受），以后 anon key 失效也不会让整条登录链路挂掉。

### 改动文件
- `app/core/config.py`：加 `wechat_appid/app_secret/link_secret` +
  `wechat_login_enabled` / `_wechat_link_key`（link_secret 空则回落 JWT_SECRET）。
  **不进 `missing_required()`** —— 微信登录是可选能力，H5 端没配也得起得来。
- `app/services/wechat.py`（新建）：只有 `code2session` +
  `placeholder_email` + `derive_password`。刻意不实现 `getuserphonenumber`
  与 `stable_token` access_token —— 不做手机号绑定，引进来是死代码。
- `app/services/supabase.py`：加 `admin_create_user`（必须 `email_confirm=True`）；
  `_headers()` apikey 回落。
- `app/schemas/auth.py`：加 `WechatLoginRequest`；`ProfileResponse.provider`。
- `app/api/v1/auth.py`：`POST /auth/wechat/login` + `_provision_wechat_user` +
  `_seed_profile`；`_profile_response` 补 provider（profiles 优先，user_metadata 兜底）。
- `.env`：加 `WECHAT_*` 占位配置（空值）。
- `docs/wechat-miniapp-login.md`：同步去掉全部手机号章节。

### 比原方案多做的两处健壮性（原方案没有）
1. **账号已存在恢复**：`admin_create_user` 若返回 422「User already registered」
   （建号成功但绑定表写入失败），用占位邮箱 + 确定性密码 `sign_in` 反查 user_id，
   而不是直接报错 —— 否则一次网络抖动就把这个微信用户永久锁死。
2. **profiles 不覆盖**：已有资料时只补 `provider`，不覆盖用户改过的昵称/头像，
   否则每次重新登录都把改名冲掉。
