## 新功能：QA 标题字段 + 标题链接口

需求：QA 带标题（解析时从文档提取，多 QA 共享一标题）；提供接口按剧本杀名称提取标题链（标题下 QA 有序）。

实现：
- `sql/dm_qa_title.sql`（新迁移，**需用户在 Supabase SQL Editor 手动执行**）：`script_dm_qa` 加 `title` 列（默认 ''）、存量回填（section_path 末级）、`idx_dm_qa_title(script_code, title)` 索引、RPC `list_dm_qa_titles(p_script_code)` 按行文顺序（d.created_at → chunk_index → q.created_at）输出扁平行，只取 is_active 文档（与检索口径一致）。
- `dm_ingest.embed_and_store`：QA 落库写 `title = section_path[-1]`。
- `dm_store.list_qa_titles(script_code)`；`dm_service.qa_title_chain()` + 纯函数 `_build_title_tree(rows)`（按 section_path 前缀建树，空路径归「未分节」，兼容逗号串脏数据）。
- schema：`QATitleItem` / `QATitleNode`（自引用，需 model_rebuild）/ `QATitleChain`，camelCase 别名。
- 接口：`GET /api/v1/scripts/{id_or_code}/dm-guide/qa-titles`（路径式）；`GET /api/v1/dm-guide/qa-titles?title=六角馆谋杀奇谋`（按名称，slugify 派生 code，同名分片自动聚合；也可传 code）。均公开只读。
- 测试 `tests/test_qa_title_chain.py` 5 例；全量 10 个测试文件 45 用例通过。

坑：本项目 FastAPI 版本用 `_IncludedRouter` 懒加载，`app.routes` 看不到子路由，验证路由要用 `app.openapi()`。

注意：本地 Celery worker 不热重载，dm_ingest 改动需重启 run_worker.py 才生效；新接口在迁移执行前会因 RPC 不存在而报错。

## 排查：登录接口 HTTP 500（出网被墙）

现象：`POST /api/v1/auth/login` 用正确 body `{email,password}` 时卡 15s 后返 500 `internal_error`；用 `{username,...}` 返 422（字段应为 email 非 username）。

根因：后端服务器（运行在国内网络）**连不上 supabase.co**——DNS 正常解析到 Cloudflare IP（104.18.38.10 / 172.64.149.246），但 TCP 443 握手超时；baidu/github 等一般外网正常。即 GFW 对 `*.supabase.co`（Cloudflare 前端）传输层封锁，Supabase 无大陆节点。`supabase_auth.sign_in()` 的 httpx POST 在 15s 超时后抛未捕获异常 → 500。

结论/约束：本项目所有依赖 supabase.co 出网的调用（登录/刷新/改密/改邮箱/GoTrue 管理接口）在该服务器上都会同样超时失败。Supabase 云在大陆"不好用"是结构性问题（Cloudflare + 无大陆区域），非配置 bug。可选方案：给后端配出网代理/VPN、自托管 Supabase 到国内服务器、或换国内 BaaS（CloudBase 等）。

代码缺口（待办）：`app/services/supabase.py` 的 `SupabaseAuth._post()` 未捕获 httpx 连接错误，建议包 try/except 返回明确 AuthError(502) 并把超时从 15s 降到 ~5s，避免每次请求卡 15s。
→ 已修复：`_post()` 增加 httpx.HTTPError 捕获（连接超时/被墙 → 明确 AuthError 502，不再 15s 卡死冒泡成 500），超时 15s→5s（AUTH_REQUEST_TIMEOUT 常量）。同文件 `verify_password` / `admin_*` 仍用裸 15s 客户端、未加固，后续可一并处理。

## 排查：dm ingest 流水线 "0 问答 / chunks 空" 假死

架构（app/tasks/dm_ingest.py）：T1 extract → T2 chunk_and_dedup（末尾设 stage_detail="得到 N 个有效块，开始生成问答对"、**写库之前**）→ chord 派发 → T3 generate_qa（队列 dm.qa）→ T4 embed_and_store（队列 dm.embed，**唯一写 script_dm_chunks 的地方**：store.insert_chunks @ ~:802）→ finalize。

用户现象：先卡在"83 个有效块"、supabase script_dm_chunks 全空 → 根因是 T4 还没跑到（worker 没消费/慢，非写库坏）。后续变为"12/83 块 / 0 问答" → 关键坑：`generate_qa`（app/services/llm.py:502）**静默吞 LLMError 返回空列表**，而 chunk 嵌入用另一套 embed 模型配置（siliconflow_embed_model）照常入库，于是"0 问答还显示成功"。

后续自愈：状态推进到"30/83 块 / 60 问答"，证明 chat 模型（SILICONFLOW_CHAT_MODEL）此前是临时故障（限流/抖动），已恢复。结论：pipeline 正常，等跑完到 83/83。

待办（可选改进）：把 generate_qa 静默降级改为失败留痕（异常摘要写 script_dm_jobs.error_message 或新增 warning 字段），避免再次出现"0 问答还显示成功"难以察觉；diagnose_dm.sql 可加列展示 warning。

## 排查：script_dm_qa 的 section_path / title 全空（已修复）

现象：最新 Word 文档《六角馆的谋杀鉴赏完整.docx》83/83 chunks、255/255 QA 的 section_path/title 全空。

根因（两层连锁）：
1. `doc_extract.py` 旧版只靠 Word 内置样式名（Heading 1/标题 1）判标题，该 docx 为手动排版未用内置样式 → 全段落判为 body。
2. 旧版把所有块 font_size 留 0.0 → `calibrate_headings` 里 font_sizes 样本为空直接 return，全局校准被跳过，文本模式兜底也不存在。

修复（三级降级策略，`app/services/doc_extract.py`）：
- 新增 `_extract_font_size(paragraph)`：从 run.font.size 取字号，字符加权中位数（Pt）。
- 新增 `_heading_level_from_text(text, is_bold)`：复用 PDF 侧 `_is_heading_like` 编号前缀正则（第X章/X.X 标题等）+ 长度与加粗约束兜底。
- `extract_shard`：填 font_size、收集 font_sizes 样本、样式未识别时走文本兜底。
- `app/services/pdf_extract.py` `classify_block` 边界修复：`font_size=0`（未知字号）时 ratio 取 1.0（原逻辑 0/body_size=0 被误判为脚注）。

验证：单元测试 + 42 用例回归全过；真实 docx《猫游记纯新人攻略新人必看(1).docx》跑完整链路检出 28 标题块、121/123 块有非空 section_path。

待办：需 force 重跑 dm pipeline（dispatch_pipeline(force=True)）让已入库文档重新解析回填 section_path/title；`scripts/diagnose_qa_empty_path.py` 为诊断脚本（httpx 直查 Supabase REST，需用 .venv python 跑）。

## 优化：QA 提取提速 + 提稳（已落地）

背景：QA 生成原用 Qwen2.5-72B + 6 chunk/批 × 5 条 = 单批最多 30 条，输出逼近 8192 token 上限经常截断 → JSON 解析失败整批丢；并发只靠 worker 数硬扛（qa worker -c 2），`llm_max_concurrency=4` 配置从未生效。

落地改动：
- `config.py`：新增 `siliconflow_qa_model="THUDM/GLM-4-Flash"`（QA 提取专用免费轻量模型，注释提示可切 Qwen/Qwen2.5-14B-Instruct）；`dm_qa_batch_size` 6→3、`dm_qa_per_chunk` 5→3（3×3 单批输出 3-5k token 稳在截断线内）。⚠️ `.env` 里也有 DM_QA_PER_CHUNK=5 覆盖，已同步改 3 并补 DM_QA_BATCH_SIZE=3。
- `llm.py`：客户端 `__init__` 加 `threading.BoundedSemaphore(llm_max_concurrency)`，`_post_sync` 整个「请求+退避重试」周期包进信号量（防 429）；`chat()` 支持按调用传 `model`；`generate_qa()` 改用 qa_model + 先试 `response_format_json=True`，个别模型不支持时自动降级纯文本重试一次（两次失败仍返回空列表，可降级不阻断流水线）。
- `supervisord.conf`：worker_qa `-c 2`→`-c 4`（前提是信号量已生效）；`run_worker.py` 本地默认并发 4→6。

验证：10 个测试文件 44 用例全过；mock 冒烟 4 例全过（model 切换 / json_object 首选项 / 降级重试 / 信号量存在）。预期收益：QA 阶段从「72B 长输出 × 2 并发」变为「免费快模型 × 4 并发 × 短输出」，总耗时降一个数量级。

注意：GLM-4-Flash 若实测 QA 质量不足，改 `SILICONFLOW_QA_MODEL=Qwen/Qwen2.5-14B-Instruct` 一行切换；重跑需重启 worker（Celery 不热重载）。

## 部署优化：Railway 免费档 4 worker 合并为单 worker（threads 池）

背景：Railway 免费档每服务仅 0.5~1GB RAM（trial 期 2 vCPU/1GB，trial 后 1 vCPU/0.5GB），原 supervisord 4 个 prefork worker（extract -c1 / chunk -c1 / qa -c4 / embed -c2）= 13 进程常驻 ~1.3GB，必然 OOM（之前 extract 的 --max-memory-per-child=300 就是 OOM 痕迹）。

落地：
- `supervisord.conf`：4 个 `[program:worker_*]` 合并为 1 个 `[program:worker]`：`celery -A app.tasks worker -Q dm.extract,dm.chunk,dm.qa,dm.embed,default --pool=threads --concurrency=8`。总并发 1+1+4+2=8 不变；内存 ~1.3GB → ~450MB（web 150 + worker 300）。
- 取舍：threads 池下 `--max-memory-per-child` 失效（prefork 专用），extract 大扫描件内存膨胀改由「降 ocr_dpi / 缩小分片」兜底；`worker_process_init` 重置连接池逻辑不再需要（同进程共享单例即可，保留无害）。
- `run_worker.py` docstring、`celery_app.py` 路由注释同步更新（不再有「4 worker 各占一队列」的说法）。
- 关键前提：prefetch=1 全局生效（config `celery_worker_prefetch=1`），threads 池多队列不会互相饿死；LLM 并发受 `llm_max_concurrency=4` 信号量限流，8 线程不会打爆配额。

验证：configparser 解析 supervisord.conf 通过（web + worker 两个 program）；celery `--help` 确认 threads 池参数合法。线上需重新部署（push 触发）后生效。
