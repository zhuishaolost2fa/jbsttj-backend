## 前端 Content-Type 真实 bug 定位与修复 + 真实服务人工验证（2026-08-06 17:30）

## 演示页「token 格式非法」诊断（2026-08-06 17:52）

用户在演示页登录/用 token 时后端报错 `token 格式非法`（code=invalid_token，抛于 `security.py:101` 的 `jwt.get_unverified_header`）。

### 根因
1. 演示页登录走后端代理 `/api/v1/auth/login` → `SupabaseAuth`，而 `SupabaseAuth._headers()`（supabase.py:187）在 `supabase_anon_key` 为空时直接 `ConfigError`。config 中 `supabase_anon_key` 默认是空串（我们至今只配了 service_role + JWT_SECRET，没配 anon key）→ **演示页「登录/注册」按钮必然失败**，用户拿不到真实 access_token。
2. 用户于是从别处复制了一段字符串（极可能是 `SUPABASE_JWT_SECRET`，或 `service_role` 的截断值）塞进「使用此 token」框 → 后端 `get_unverified_header` 解析失败 → 报「token 格式非法」。
3. 后端 JWT 校验要求：header 可解析出 alg；alg=HS256 时用 JWT_SECRET 校验；payload 必须含 `exp`+`sub`，且 `aud`==`authenticated`（默认 audience），否则对应报 token 校验失败/受众不匹配，而非格式非法。

### 解法
新增 `scripts/make_user_token.py`：用 `service_role` key 经 Supabase Admin API 真实创建一个验证用户 `verify@jbsttj.local`（email_confirm=true），再用 `JWT_SECRET` 以 HS256 签发结构合法的 access_token（sub=用户UUID / email / role=authenticated / aud=authenticated / iat / exp=now+3600），并自动调运行中的 `:8000/api/v1/auth/me` 验证后端放行。
- 运行结果：用户创建成功 id=0415f1f1-...，`auth/me` 返回 **200**，身份正确。用户复制该 token 粘贴到演示页「使用此 token」即可走真实 JWT 链路 + 浏览器直传。
- 说明：因 `schema.sql` 已去掉 user_id 对 auth.users 的 FK，即使不创建真实用户、只签一个合法 UUID sub 的 token 也能跑通（更省事），但建真实用户更贴近真实环境。

- 若把规则前缀改成 `uploads/` 以匹配，则"文件 2 天后删除"会清除**所有已完成上传文件**（非仅临时），除非该 bucket 是纯临时桶，否则应只保留"碎片清理"一条，避免误删正式文件。
- OSS 生命周期规则**次日 0 点左右才执行**，非即时，别指望加完立刻生效。
- 如需"仅特定文件（如临时 PDF）定时过期"，应在后端为这类上传用独立前缀（如 `temp/`）或打 tag，再做精细化规则；当前所有上传共用 `uploads/` 前缀。

## 新增「临时文件 / 永久文件」两条上传接口（2026-08-06 18:06）

用户要求生成临时文件上传接口和永久文件上传接口，以便后续单独对临时文件做 OSS 生命周期过期清理。实现方式 = 用 object_key 前缀区分命名空间（不改表结构，无需重跑 schema.sql）：

### 改动
- `app/core/config.py`：新增 `temp_upload_prefix: str = "temp"`（永久仍是 `upload_prefix="uploads"`）。
- `app/schemas/upload.py`：`InitUploadRequest` 增加 `upload_type: Literal["temporary","permanent"] = "permanent"`；`InitUploadResponse` 增加回传 `upload_type`。
- `app/services/upload_service.py`：`init_upload` 按 `upload_type` 选前缀（temporary→temp_upload_prefix，否则 uploads）；全新任务的 `build_object_key` 用该前缀；任务 `metadata` 里额外记 `upload_type` 便于排查；`upload_type` 回传到响应。
- `app/services/repository.py`：`find_by_hash`/`find_resumable` 增加可选 `key_prefix` 参数，按 `object_key like.{prefix}/*` 限定命名空间 → **关键**：避免永久上传以秒传/续传复用临时对象（否则临时对象被生命周期删后拖垮永久文件）。
- `app/api/v1/uploads.py`：新增 **`POST /api/v1/uploads/temp/init`**（强制 `upload_type="temporary"`，与 `/init` DRY 复用同一 service）；原 `/init` 默认 permanent，也可显式传 `upload_type:"temporary"`。
- `frontend/index.html`：上传区新增「临时文件（自动过期清理）」勾选框，`/uploads/init` 请求体带 `upload_type`（勾选=temporary，否则=permanent），方便人工验证。

### 真实接口验证（运行中 uvicorn :8000，服务通道 `X-API-Key + X-User-Id`）
三条 init 全部 201，object_key 前缀正确分流：
- `POST /uploads/init`（默认）→ `uploads/{uid}/2026/08/{uuid}.pdf` / upload_type=permanent
- `POST /uploads/init` 带 `upload_type:"temporary"` → `temp/{uid}/2026/08/{uuid}.pdf`
- `POST /uploads/temp/init` → `temp/{uid}/2026/08/{uuid}.pdf`
**结论：临时文件稳定落在 `temp/` 前缀，用户只需把 OSS 生命周期规则前缀从 `pdf/` 改为 `temp/` 即可命中。**

### 给用户的生命周期规则建议
- 临时文件规则：前缀 `temp/`，「文件：最后修改 2 天后删除」+「碎片：生成 2 天后删除」（碎片清理防 OSS 空计费，推荐保留）。
- 永久文件无需规则（落在 `uploads/`，不被匹配）。
- 生效：规则**次日 0 点**左右扫描执行，非即时。
