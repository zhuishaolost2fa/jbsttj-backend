## 本地联调架构改造（免部署 Railway）

目标：前端 H5（8010）直接联调本地后端（8000），不再依赖部署 Railway。

改动：
- `app/core/config.py`：env_file 分层为 `(".env", ".env.local")`，优先级 真实环境变量 > .env.local > .env；新增 `redis_url` 字段，Railway 注入 `REDIS_URL` 且 result backend/去重 URL 仍为内置默认值时自动派生（db0/db1）。
- 新增 `.env.local`（已 gitignore）：CORS 放行 8010；`CELERY_EAGER=false`；broker/backend/去重全部指向本地 Redis db2/db0/db1 —— 本地单 Redis 模式，免 RabbitMQ。
- 新增 `run_worker.py`：本地 worker 启动脚本，单进程消费全部 5 条队列，默认 `--pool=threads -c 4`（prefork 在 Windows 不可用）；可用 `LOCAL_WORKER_QUEUES/POOL/CONCURRENCY` 覆盖。
- README 增加「7. 本地联调」一节（三档模式：eager 零依赖 / 单 Redis 联调 / docker-compose 完整版）；`.env.example` 同步说明分层与 REDIS_URL。

验证：venv 下加载配置确认 .env.local 覆盖生效（broker=redis db2、eager=False、CORS 含 8010）；REDIS_URL 派生逻辑经模拟验证；FastAPI + celery_app 装配无报错。

注意：本地与线上共用同一套 Supabase/OSS/SiliconFlow，本地解析入库的数据线上可见。

## 排障：本地解析一直"排队中"

现象：任务派发后卡在 queued，`dm.extract` 队列积压 1 条无人消费。
两层原因：
1. 本地没起 worker（只起了 API 和 Redis）。
2. 起了 worker 仍不消费 —— `run_worker.py` 里 celery 短选项用了等号写法 `-Q=dm.extract,...`，`=` 被吞进首个队列名，worker 实际绑定到假队列 `=dm.extract`（banner 里可见 `.> =dm.extract`），真实 `dm.extract` 无人消费。

修复：argv 改为「选项与值分两个 token」（`"-Q", queues`），并删掉 Redis db2 里残留的 `_kombu.binding.=dm.extract` 假绑定。重启后积压任务立即被消费，全流水线跑通（105 chunks / 18 QA batches）。

教训（已写进 run_worker.py 注释）：celery/click 短选项禁止 `-X=value` 写法。

## 修复：同名分片手册导入互相覆盖

用户场景：《六角馆谋杀奇谋》拆成两个同名文档导入（两个同名剧本记录，不同 script_id、相同 script_code），后导入的把先导入的"覆盖"了。

根因：`dm_service.trigger_ingest` 的防重查询 `find_active_job(script_id, script_code=script_code)` 按 script_code 查在跑任务。分片 B 导入时查到分片 A 正在跑的任务，且 object_key 不同，走进"文件已更换"分支把 A 的任务取消 —— A 的流水线被杀，QA 永远建不全。

修复：防重粒度改为只按 script_id 查（`store.find_active_job, script_id`）。同 script_id 内"换文件重传取消旧任务""同文件重复触发复用任务"语义不变；不同 script_id 的同名分片互不干扰，检索层本就按 script_code 聚合（match_dm_chunks/match_dm_qa 按 code 过滤 + is_active join），QA 全部保留。

新增 tests/test_ingest_same_title_shards.py（3 个用例）；全部 9 个测试文件 40 个用例通过。

注意：同一剧本记录（同 script_id）内换文件仍是"新版取代旧版"语义（旧文档 is_active=false 不参与检索），同名分片必须用两个剧本记录导入。
